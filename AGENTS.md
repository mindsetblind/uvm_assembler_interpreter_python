# Правила работы над практической работой №3

Эти инструкции действуют для всего проекта. Общаемся и ведём документацию
на русском языке. Реализация — Python.

## Источник требований

Задание: `ИКБО-64-25 (3).pdf`, вариант **29**.
Общие требования: стр. 4; критерии оформления: стр. 5–7;
спецификация УВМ и пять этапов: стр. 120–123.
Перед изменением реализации сверяться с соответствующим этапом PDF.
Не подменять требования предположениями или текущим кодом/README.
Неоднозначные технические решения явно описывать в README.

## Ветки и история Git

- Каждый этап выполнять в отдельной ветке: `stage-1`, `stage-2`,
  `stage-3`, `stage-4`, `stage-5`. Это дополнительное правило пользователя.
- Перед изменениями проверять текущую ветку и рабочее дерево.
  Не разрабатывать этапы непосредственно в `main`.
- Следующий этап начинать от результата предыдущего: от актуальной `main`,
  если предыдущий этап уже влит, либо от его ветки.
- Не смешивать несколько этапов в одном коммите.
- По завершении каждого этапа проверить результат и сохранить отдельным
  коммитом с подробным сообщением по Conventional/Scoped Commits.
  Пример: `feat(asm): parse stage-1 assembly into intermediate representation`.
  В теле сообщения описать изменения и выполненные проверки.
- Не объявлять этап полностью завершённым, пока нет проверок и коммита.
- Не переписывать историю и не терять пользовательские изменения.
- Задание требует публично доступного Git-репозитория с историей этапов.
  Локальный `git init` сам по себе это требование не выполняет.
- На момент создания этих правил файлы этапа 1 ещё не закоммичены,
  выбрана `main`. Перед дальнейшей работой над этапом 1 перейти в `stage-1`;
  первый коммит реализации этапа 1 должен быть в этой ветке.

## Структура и документация

- Обязательны `README.md`, `.gitignore`, `src/`, `tests/` и скрипт запуска
  `run.sh`, `run.bat` или `Makefile`. В этом проекте используется `run.sh`.
- README должен содержать общее описание, описание всех функций и настроек,
  команды сборки и запуска тестов, примеры использования.
- В README описывать язык ассемблера, CLI обоих инструментов, семантику
  команд, порядок операндов, модель памяти и формат дампа по мере реализации.
- Обновлять документацию при каждом изменении поведения.
  Отличать реализованные возможности от запланированных.
- Исходники размещать в `src/`, тесты в `tests/`, программы-примеры
  на языке ассемблера в `programs/`.
- Не добавлять в Git архивы, бинарные файлы (включая PDF задания и `.bin`),
  служебные файлы Python, артефакты сборки и настройки редакторов.
  Соответствующие исключения поддерживать в `.gitignore`.
- Сгенерированные дампы и другие результаты запусков оставлять вне Git;
  ожидаемые результаты проверять тестами и описывать текстом.

## Критерии качества кода

- Файл: не более 1000 строк.
- Строка Python: не более 80 символов, считать символы, а не UTF-8 байты.
  Общий предел строк кода — 120 символов; для Python действует более строгий.
- Функция: не более 40 строк и не более 7 аргументов.
- Цикломатическая сложность: не более 10.
- Документация Python — docstring, а не заменяющий её комментарий.
- Не использовать магические числовые литералы в сравнениях:
  коды операций, размеры и границы представлять именованными константами.
- Имена Python должны соответствовать PEP 8.
- Если появятся другие языки, применять критерии стр. 5–7 PDF:
  JavaScript — строки до 80 символов, Kotlin/Rust — до 100,
  остальные — общий предел 120; функции до 40 строк, аргументов до 7,
  сложность до 10, стандартные для языка имена и средства документации.

## Спецификация УВМ: вариант 29

- Каждая команда занимает **5 байт**. Поле A — биты 0–5.
- Загрузка константы: A=38, B — биты 6–31 (26 бит).
  Поместить B на стек.
- Чтение памяти: A=63, B — биты 6–18 (13 бит).
  Снять адрес со стека, прибавить B, прочитать память и поместить на стек.
- Запись памяти: A=62, поля B нет.
  Сначала снять значение, затем адрес; записать значение по этому адресу.
- `pow()`: A=14, B — биты 6–36 (31 бит).
  Первый снятый операнд — основание, второй — показатель;
  записать результат в память по адресу B.
- Память команд и данных должна быть объединена.
- Машинное представление должно точно совпадать с тестами PDF;
  для данных команд используется little-endian, неиспользуемые биты нулевые.
- Контрольные последовательности:
  - A=38, B=439: `0xE6, 0x6D, 0x00, 0x00, 0x00`.
  - A=63, B=201: `0x7F, 0x32, 0x00, 0x00, 0x00`.
  - A=62: `0x3E, 0x00, 0x00, 0x00, 0x00`.
  - A=14, B=782: `0x8E, 0xC3, 0x00, 0x00, 0x00`.

## Результаты каждого этапа

### Этап 1 — `stage-1`: промежуточное представление

- CLI ассемблера принимает путь к исходнику, путь к двоичному результату
  и режим тестирования.
- Человекочитаемый алгебраический синтаксис в духе языков высокого уровня
  поддерживает все четыре команды и описан в README.
- Транслятор преобразует текст во внутреннее представление.
- Только на этом этапе режим тестирования выводит поля и значения IR
  в соответствии с тестами спецификации.
- Программа-пример покрывает все тесты спецификации;
  продемонстрировать совпадение полей и значений.
- Проверки и отдельный оформленный коммит обязательны.

### Этап 2 — `stage-2`: машинный код

- Преобразовать IR в машинное представление и записать двоичный файл.
- Вывести число ассемблированных команд.
- В режиме тестирования выводить байты в формате тестов спецификации.
- Подготовить исходник, дающий все четыре контрольные последовательности,
  и проверить побайтовое совпадение.
- Проверки и отдельный оформленный коммит обязательны.

### Этап 3 — `stage-3`: интерпретатор и память

- CLI интерпретатора принимает путь к бинарной программе,
  путь к дампу памяти и диапазон адресов дампа.
- После исполнения сохранять дамп указанного диапазона в **CSV**.
- Реализовать объединённую память команд и данных.
- Цикл интерпретатора: чтение команды, декодирование в IR, выполнение.
- Поддержать загрузку константы, чтение и запись памяти.
- Написать и выполнить программу копирования массива с одного адреса
  на другой, проверить результат.
- Проверки и отдельный оформленный коммит обязательны.

### Этап 4 — `stage-4`: АЛУ

- Реализовать выполнение `pow()`.
- Написать и выполнить тестовую программу с вычислением и сохранением
  результата в память; проверить корректность сохранённого значения.
- Проверки и отдельный оформленный коммит обязательны.

### Этап 5 — `stage-5`: тестовая задача

- Написать, ассемблировать и исполнить программу поэлементного `pow()`
  над вектором длины **9** и числом **157**.
- Результаты записать в **новый вектор**.
- Создать три примера программ с различными входными данными.
- Продемонстрировать по дампам памяти соответствие результатов задаче.
- Проверки и отдельный оформленный коммит обязательны.

## Проверка перед завершением этапа

- Выполнить `./run.sh test` и соответствующие этапу примеры через CLI.
- Проверять фактический результат: IR, точные байты, значения памяти
  или дамп в зависимости от этапа; не ограничиваться успешным кодом выхода.
- Проверить ограничения оформления и содержимое Git diff/status.
- В сообщении пользователю указать сделанное, результаты проверок,
  текущую ветку, коммит и оставшиеся невыполненные требования.
